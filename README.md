# Delim — совместные расходы в MAX

Категория: **«Досуг и развлечения»**.

Delim — бот и Mini App в MAX для учёта общих расходов во время поездок, походов, мероприятий и другого совместного досуга. Организатор создаёт план, приглашает участников, добавляет траты вручную или по чеку, а приложение рассчитывает баланс и показывает, кто кому должен вернуть деньги.

## Назначение решения

Delim заменяет таблицы, заметки и расчёты в переписке единым пространством внутри MAX. Решение позволяет:

- создать план совместного досуга и задать бюджет;
- пригласить участников ссылкой;
- добавить расход и разделить его поровну, по долям, процентам, точным суммам или позициям чека;
- распознать чек по фотографии либо получить данные по фискальному QR-коду, а также проверить и исправить результат распознавания до создания расхода;
- увидеть личный баланс и получить минимальный набор переводов для возврата средств;
- отметить возврат, корректировку или погашение;
- экспортировать историю в CSV, PDF или XLSX;
- получать уведомления и выполнять действия в чате с ботом MAX.

Все суммы MVP учитываются в рублях (`RUB`).

## Основной пользовательский сценарий

1. Пользователь открывает бота Delim в MAX и запускает Mini App.
2. Создаёт план, например «Поездка в Казань», указывает даты, место и планируемый бюджет.
3. Приглашает друзей по ссылке созданной в mini App.
4. Добавляет расход вручную, фотографирует чек камерой/загружает его из галереи либо сканирует QR-код на чеке через сканер QR MAX.
5. Проверяет продавца, дату, сумму и позиции распознанного чека.
6. Выбирает плательщика, участников и способ разделения расхода.
7. Сохраняет и подтверждает расход. Только подтверждённая операция влияет на баланс.
8. После завершения плана открывает «Кому вернуть», создаёт погашение, а получатель подтверждает его.
9. При необходимости выгружает историю группы в файл.

Ожидаемый результат: участники видят одинаковую историю расходов, актуальный баланс и понятный план переводов, позволяющий погасить задолженности.

## Быстрый локальный запуск

### Требования

- Docker Engine с Docker Compose v2;
- GNU Make;
- Linux `x86_64` рекомендуется для нативного PaddleOCR.

Для запуска через Docker локально устанавливать Go, Python и Node.js не нужно.

### Подготовка окружения

```bash
cp .env.example .env
```

Для локальной проверки задайте в `.env` непустые и разные значения `GATEWAY_SESSION_SECRET`, `GATEWAY_INVITE_SECRET` и `GATEWAY_LAUNCH_SECRET`. Тестовые значения допустимы только локально.

### Одна команда запуска всех локальных компонентов

```bash
make dev-up
```

Команда поднимает PostgreSQL и MinIO, создаёт приватный бакет, применяет миграции, собирает и запускает Mini App, Gateway, Core и Document, затем ждёт успешных healthcheck.

- Mini App: <http://localhost:8081>
- Gateway: <http://localhost:8080>

> Production-like Mini App на `:8081` ожидает подписанный контекст MAX. Для проверки без MAX используйте тестовые данные и Vite-режим ниже.

## Состав и архитектура

```text
MAX Bot / MAX Mini App
          │ initData, webhook, HTTPS/JSON
          ▼
      Gateway (Go) ───────── gRPC ─────────► Core (Go)
          │                                     │
          │ gRPC                                │ финансовые данные
          ▼                                     ▼
   Document (Python) ─────────────────────► PostgreSQL
          │
          ├── PaddleOCR / OpenCV
          └── MinIO: изображения чеков и экспорты
```

| Компонент | Назначение |
|---|---|
| Mini App | React-интерфейс внутри MAX: планы, участники, траты, чеки, баланс и экспорт |
| Gateway | Публичный HTTP API, MAX `initData`, сессии, webhook, уведомления, rate limiting и вызовы внутренних сервисов |
| Core | Основная бизнес-логика для групп, ролей, расходов, распределений, баланса, корректировок и погашений |
| Document | Хранение чеков, QR, preprocessing, фоновый OCR, парсинг позиций и создание экспортов |
| PostgreSQL | Финансовые записи, метаданные документов, OCR-задачи и служебные данные Gateway |
| MinIO | Объектное хранилище оригиналов чеков и файлов экспорта |

Mini App обращается только к Gateway. Gateway вызывает Core и Document по gRPC. Document не создаёт финансовые операции: результат OCR становится расходом только после явного подтверждения пользователя.

Контракты находятся в [`proto/`](proto/) и [`api/openapi.yaml`](api/openapi.yaml), подробная схема — в [`docs/architecture.md`](docs/architecture.md).

## Внешние сервисы и интеграции

### MAX — необходим для основного сценария

Для проверки нужны:

1. действующий бот и зарегистрированная Mini App в MAX;
2. публичные HTTPS-адреса Mini App и webhook Gateway;
3. заполненные `MAX_BOT_TOKEN`, `MAX_BOT_USERNAME`, `MAX_WEBHOOK_SECRET`, `MAX_WEBHOOK_URL`, `MAX_MINI_APP_URL`;

После настройки:

```bash
make max-setup
make max-check
```


### Проверка чека по фискальному QR — необязательная интеграция

При наличии `PROVERKACHECKA_TOKEN` Document обращается к `proverkacheka.com`, чтобы получить проверенные позиции чека. Без токена решение использует локальный QR-reader и PaddleOCR. Для проверки интеграции нужны интернет и действующий токен.

### Модели OCR

PaddleOCR работает локально внутри Document. При первой сборке image модели загружаются из внешнего хранилища Paddle; после сборки inference выполняется локально. Для сборки с нуля нужен интернет.

## Работа с данными

- PostgreSQL использует одну БД `delim`; Core, Document и Gateway имеют отдельные таблицы и миграции.
- Core — компонент, изменяющий финансовую историю и учет средств.
- Деньги хранятся целым числом в копейках, валюта MVP — `RUB`.
- Расход влияет на баланс только после подтверждения; отменённая трата из расчётов исключается.
- OCR выполняется фоновой задачей со статусами `queued`, `processing`, `completed`/`ready`, `failed`; чтение чека не ждёт inference.
- Изображения чеков и экспорты находятся в приватном бакете MinIO `receipts`. Скачивание идёт через авторизованный Gateway.
- Срок хранения оригинала чека по умолчанию — 30 дней; очистку выполняет Document.
- Миграции применяются идемпотентно командой `make dev-up`.
- `make down` сохраняет Docker volumes, `make clean` безвозвратно удаляет локальные данные без бэкапа.

Резервная копия локальной БД:

```bash
make db-backup
make db-restore FILE=backups/<имя-файла>.dump
```

## Пошаговая проверка MVP

### Основной сценарий в MAX

1. Открыть действующего бота Delim и запустить Mini App.
2. Убедиться, что вход выполнен без ручного логина.
3. Создать план «Поход на выходные», указать место, даты и бюджет.
4. Пригласить второго участника и открыть план из его MAX-аккаунта.
5. Добавить ручной расход, выбрать плательщика и разделить сумму поровну.
6. Подтвердить расход и проверить баланс обоих участников.
7. Считать фискальный QR либо выбрать фотографию чека.
8. Дождаться экрана проверки, исправить позицию и продолжить к расходу.
9. Сохранить и подтвердить расход.
10. Открыть «Кому вернуть», создать погашение и подтвердить его вторым участником.
11. Подготовить CSV/PDF/XLSX и скачать файл либо отправить его в нужный чат.

### Локальная проверка без MAX

1. Выполнить `make dev-up`.
2. Выполнить `make demo-seed`,  `make web-install`, `make web-dev`.
3. Открыть <http://localhost:5173> и выбрать демо-группу.
4. Проверить бюджет, расходы и баланс.
5. Открыть ожидающий расход, изменить и подтвердить его.
6. Добавить новую трату с другим способом распределения.
7. Создать корректировку или возврат.
8. Создать погашение и проверить пересчёт баланса.
9. Подготовить и скачать экспорт.

Автоматическая интеграционная проверка запущенного stack:

```bash
make smoke
```

Она проверяет расходы, баланс, погашения, корректировки, чеки, экспорт и деградацию при недоступном Document. MAX проверяется только при заданном `MAX_BOT_TOKEN`.

## Примеры ожидаемого поведения

- Ввод суммы `1500` принимается как `1500,00 RUB`.
- Расход «На проверке» не меняет итоговый баланс; после подтверждения баланс пересчитывается.
- Отменённый расход остаётся в истории, но не влияет на расчёты.
- Загрузка чека сразу возвращает идентификатор, UI показывает `queued → processing → готово`, а другие экраны отвечают во время OCR.
- До создания расхода можно изменить итог, дату, продавца, позиции и участников чека.
- «Кому вернуть» предлагает переводы без лишних встречных платежей.
- Повторный webhook MAX не создаёт дубликат операции.
- При недоступном Document ручные расходы и баланс работают, а чек показывает понятную ошибку.

## Ограничения MVP

- Поддерживается только RUB.
- Основной сценарий зависит от MAX и публичного HTTPS-развёртывания; 
- OCR не гарантирует абсолютную точность, поэтому предусмотрена ручная проверка.
- Нативный PaddleOCR рассчитан на Linux `x86_64` CPU; первый запуск может быть дольше из-за прогрева.
- Локальный OCR worker обрабатывает задания последовательно.
- Проверенные позиции по QR зависят от стороннего API; при сбое используется локальный OCR.
- MVP не бронирует билеты, жильё или мероприятия и не содержит каталога досуга.
