# Материалы сдачи: «Делим досуг»

## Назначение и пользователь

Delim — Mini App и бот в MAX для организатора небольшой совместной поездки,
похода или мероприятия. Чеки и договорённости о расходах часто теряются в
чате, а участники не видят общий итог. Результат сценария — подтверждённые
траты, баланс группы и план минимального числа погашений.

Каталог событий, бронирование и внешние туристические справочники в MVP не
подключены.

## Основной сценарий проверки в MAX

1. Открыть бота Delim и запустить Mini App.
2. Создать группу «Поход на выходные».
3. Пригласить участников ссылкой либо привязать MAX-группу и синхронизировать участников.
4. Указать плановый бюджет активности и открыть его сводку на дашборде.
5. Добавить расход или чек, проверить OCR-поля и явно подтвердить расход.
6. Добавить несколько трат с разными плательщиками и сравнить план/факт бюджета.
7. Открыть «Баланс» и «Погашения», создать перевод по плану и подтвердить его получателем.

Ожидаемый результат: расходы подтверждены, баланс рассчитан, план содержит
переводы, сводящие баланс к нулю.

## Запуск

```sh
cp .env.example .env
make dev-up
```

`make dev-up` через Docker поднимает БД/MinIO, применяет миграции, собирает и
запускает весь локальный stack. Локальный production-like web доступен на
`http://localhost:8081`. Для Vite и synthetic demo-сессии после этого используйте
`make demo-seed && make web-install && make web-dev`. Остановка и повторный
запуск: `make down`, затем `make dev-up`. `make demo-seed` создаёт синтетическую группу и локальную
demo-сессию в игнорируемом `web/miniapp/.env.local`.

Локальные порты: web `8081`, Vite `5173`, Gateway `8080`, Core gRPC `50051`,
Document gRPC `50052`, PostgreSQL `5432`, MinIO API `9000`, MinIO console `9001`.
Переменные перечислены в `.env.example` и `deployments/prod/.env.example`.
Рабочие токены и секреты в репозитории не фиксируются.

Основные параметры окружения: `POSTGRES_*` и `DATABASE_URL` для PostgreSQL,
`MINIO_*` для Object Storage, `CORE_GRPC_ADDR` и `DOCUMENT_GRPC_ADDR` для
межсервисных адресов, `GATEWAY_SESSION_SECRET` и `GATEWAY_INVITE_SECRET` для
сессий/invite, `GATEWAY_CORS_ALLOWED_ORIGINS` для origin Mini App,
`DELIM_GATEWAY_URL` для web, `MAX_BOT_TOKEN`, `MAX_BOT_USERNAME`,
`MAX_WEBHOOK_SECRET`, `MAX_WEBHOOK_URL` для MAX. Полный список и значения
по умолчанию находятся в env.example файлах.

## Архитектура, API и данные

`MAX → Mini App → Gateway → Core`; для чеков Gateway обращается к Document,
после ручной проверки результат создаёт расход через Core. Core — источник
истины для ledger и погашений; PostgreSQL хранит metadata и финансовые записи,
MinIO — приватные чеки и экспорты. Контракт API — `api/openapi.yaml`.

Внешняя проверка требует Bearer-сессию из `POST /api/v1/auth/max`, где
`init_data` выдаётся MAX. Публичный HTTPS URL, тестовый MAX-доступ и commit hash
передаются отдельно перед сдачей и намеренно не записываются в этот репозиторий.

## Ограничения и масштабирование

MVP не бронирует билеты и не имитирует внешние каталоги. OCR зависит от
Document; при сбое доступен ручной ввод, Core продолжает работать. Demo-данные
синтетические. Ядро (группы, split, ledger, settlement) переносится между
поездкой, походом и мероприятием; переменная часть — категории расходов,
справочники, региональные интеграции и правила организации. Пилот — одна
MAX-группа организатора; метрики: завершение сценария, доля подтверждённых трат,
время до баланса и исправления OCR.

## Docker и проверка

После применения миграций raw compose-команда для повторного запуска stack:

```sh
docker compose --env-file .env -f deployments/dev/compose.yaml up --build
```

Конфигурация: `deployments/dev/compose.yaml`, `deployments/prod/compose.yaml`,
`build/Dockerfile*`, `.dockerignore`, `.env.example`. Перед фиксацией версии:

```sh
make audit
make smoke
```

Полный порядок демонстрации и fallback описан в `docs/demo.md`.
